# Git 分支与合并

Git 是分布式版本控制系统，每个开发者本地都有完整的仓库历史。分支是 Git 的核心能力之一，它让并行开发互不干扰。

## 分支的本质

Git 的分支实际上只是一个指向某次提交的可移动指针，创建分支几乎不消耗资源。HEAD 指向当前所在分支。每次提交都会让当前分支指针向前移动，因此可以在同一个仓库里同时维护多条开发线。

## merge 合并

merge 把另一个分支的改动合并进当前分支。如果两个分支的修改没有冲突，Git 会自动生成一个合并提交，保留两条开发线的完整历史。如果当前分支自目标分支分出后没有新提交，Git 会做快进合并，直接把指针前移，不产生合并提交。

merge 的优点是保留真实的分支拓扑，历史可追溯；缺点是分支多时提交图会比较乱，出现大量交叉的合并提交。

## rebase 变基

rebase 把当前分支的提交逐个在目标分支的最新提交之上重新应用，相当于改写提交的父节点。结果是历史变成一条直线，非常干净。代价是提交的哈希值会改变，如果在共享分支上已经推送过，不要对公共分支做 rebase，否则会给协作者带来麻烦。

## 合并冲突

当两个分支修改了同一文件的同一区域，Git 无法自动决定保留哪一份，就会产生合并冲突。冲突文件里会出现标记，分别标记当前分支的内容和另一分支的内容。解决方法是人工编辑保留正确内容、删除冲突标记，然后 git add 标记为已解决，最后提交。冲突期间不要慌，可以随时用 git merge --abort 放弃合并回到之前的状态。

## 实践建议

功能开发从主干拉出特性分支，完成后通过合并请求评审再合入；合并前先同步主干，尽量把冲突解决在本地。提交信息要说明做了什么和为什么做，一个提交只做一件事，方便回滚和审查。
