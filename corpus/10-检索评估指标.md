# 检索评估指标：Recall@K 与延迟

检索系统的质量不能凭感觉判断，需要用可重复的评估集和明确的指标来衡量。一个最小但有效的评估应包含三部分：带标注的测试问题、检索质量的指标、以及性能延迟指标。

## Recall@5

Recall@K 指在检索返回的前 K 个结果里，是否命中了我们期望的来源文档或分块。对单条问题来说命中记 1，不命中记 0，所有问题的平均值就是 Recall@K。工程上常写写 Recall@5，表示只看前五个结果。

定义命中需要小心：只判断文档 id 可能过于宽松，因为一篇文档有多个分块，检索到任意分块都算命中，可能掩盖分块边界的问题。更严格的评估会同时检查期望关键词是否出现在命中分块中，只有命中的分块确实包含答案相关内容才算成功。这个口径要在 README 里写清楚，避免指标看起来虚高。

## 引用可溯源率

引用可溯源率统计回答中的引用标记能成功映射到真实分块的比例。评估脚本应该独立地获取全部合法分块 id 集合（例如通过文档详情接口），然后检查每一条引用里的 chunk_id 是否存在、分块文本是否非空，而不是直接相信问答接口自报的 traceability 字段。两类指标分开统计，才能分别定位检索问题和生成问题。

## 平均延迟与分位数

延迟用每次请求的耗时统计，报告平均值的同时最好给出中位数和 95 分位。平均延迟容易被少数慢请求拉高，p95 更能反映用户体验。测量时要区分检索延迟和端到端延迟：检索延迟只算 BM25 与向量打分，端到端延迟包含生成回答的时间。评估结果应保存为 JSON，包含每道题的检索结果、耗时和汇总指标，方便回归对比。

## 评估集设计

评估集应覆盖不同主题、不同问法，问题数量不必多但要有代表性，二十道题左右就能看出明显问题。每道题标注期望文档和关键词，评估脚本自动判断命中。评估前要确保语料已经全部入库并且状态为 ready，否则会把「还没入库」误判为「检索失败」。
